# Nani 打卡与打卡管理

## Scope

- scope: 补齐护工端服务打卡与管理端打卡管理的端到端工作流。
- affected users: 一线护工、值班主管、护理组长、机构运营。
- changed behavior: 护工执行任务前先完成服务打卡，admin 可统一查看打卡状态、异常和主管确认结果。
- dependent systems: nursing-nani-app、nursing-admin-v2、本地 mock workflow store。
- verification: `npm run docs:build`、nani `flutter analyze` + `flutter test`、admin `npm run lint` + `npm run build`。
- rollback: 回退新增页面、导航入口、workflow 字段和本文件。

## 模块目标

把“到场确认 -> 服务执行 -> 异常说明 -> 主管复核”收敛成单一闭环，避免护工只做执行备注、不留打卡证据，也避免 admin 只能看任务状态、看不到服务到场与异常打点。

## 核心能力

- 护工端在任务执行前完成到场打卡，记录打卡方式、服务位置和异常备注。
- 护理执行页承接打卡摘要，而不是从零开始填写执行信息。
- 管理端按班次、状态、异常和主管确认结果查看打卡记录。
- 已完成或异常打卡记录需要进入主管确认，而不是停留在“任务已完成”的单一状态。

## 关键流程

1. 护工从首页、任务中心或长者详情进入服务打卡。
2. 在护工端确认任务对象、打卡方式和到场状态，必要时补充异常原因。
3. 打卡摘要带入护理执行页，执行结果继续进入交接班或报警链路。
4. 管理端按打卡记录查看待执行、服务中、已完成、异常待复核和已确认状态。
5. 主管对异常或已完成记录做闭环确认，形成可追溯的管理留痕。

## 验收方向

- 护工端存在明确的打卡入口，且打卡后能把摘要带到护理执行页。
- 未打卡也能直接执行的旧路径不能成为主路径；至少要有显式补录说明。
- 管理端能看到打卡状态、服务人、班次、异常原因和主管确认结果。
- AI 不直接替代打卡、结案或主管确认。

## 当前实现映射

- nani 侧已经落地独立服务打卡页，入口来自首页、任务中心和长者详情，不再把护理任务直接送入执行页。
- 护理执行页已经消费 `CareClockInDraft`，把到场方式、位置和异常说明带入后续执行摘要。
- admin 侧已经落地 `/nursing/checkin` 打卡管理台，支持状态筛选、班次筛选、异常查看和主管确认。
- 当前实现仍基于各端本地 mock store，目标是先固化产品流程与页面语义，再对接真实接口。

## 后续接口对接原则

- 本阶段不把 mock 字段直接视为后端契约，后续接接口前需要单独做字段对齐和兼容性评审。
- 后端接入优先复用当前状态语义和页面健康信号，不回退产品流程。
- 真实接口上线前，文档中的流程、字段和异常路径继续以当前前端实现为准。

## 边界说明

- 当前阶段仍为前端 mock workflow，不引入真实定位、扫码硬件或后端工单契约。
- 打卡管理不替代排班、绩效或考勤结算，只服务于护理执行闭环。
- 高风险异常仍需走现有报警或交接班链路，不在打卡页直接结案。
