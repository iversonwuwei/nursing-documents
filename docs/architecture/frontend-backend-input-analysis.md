# 三端前端输入分析与后端约束

## 交付 framing

- scope: 基于 admin、family、nani 三个前端工程的当前能力与既有平台文档，提炼 backend 工程必须满足的领域边界、接口模式与治理约束。
- affected audience: 平台架构师、后端负责人、BFF 开发、前端负责人、测试与 SaaS 交付团队。
- validation: 文档需与现有三端 README、交付设计文档、平台架构文档和模块映射保持一致，并通过 `npm run docs:build`。
- rollback: 回退本文和关联索引修改，恢复到原有平台级文档集合。

## 目标

本文不描述具体数据库表，也不直接替代 API 契约。它的作用是把三个前端工程已经暴露出的 backend 需求，收敛为可执行的后端约束输入。

## 前端输入总览

| 前端 | 当前定位 | 交互特征 | 对 backend 的直接要求 |
| --- | --- | --- | --- |
| admin | 运营与治理后台 | 聚合查询 + 审批命令 + 配置管理 + AI 审计 | 强聚合读模型、跨域 workflow、权限治理、审计追踪、多租户运营视图 |
| family | 家属协同端 | 只读摘要 + 探视预约 + 账单与消息 + AI 解释 | 关系绑定、隐私裁剪、可解释摘要、弱写入强通知、面向家属的 BFF |
| nani | 护工执行端 | 高频任务执行 + 健康录入 + 报警响应 + 交接班 | 幂等写入、移动端鉴权、任务中心、离线容错、低延迟命令链路 |

## Admin 输入分析

### 业务特征

- Admin 已覆盖长者、健康、探视、员工、房间、机构、设备、物资、财务、报警、活动、AI 运营中心等模块。
- 多个页面已经形成“新建 -> 待确认 -> 激活”的闭环，这要求 backend 不能只提供 CRUD，而要提供对象状态机和审批动作。
- Dashboard、analytics、health、AI assistant 等页面不是单服务页面，而是聚合视图，天然需要 BFF 或 query composition。

### 后端约束

- 不能按页面拆服务，必须按领域拆分。
- 需要 Admin BFF，负责跨服务拼接、角色裁剪、查询缓存和页面级 DTO。
- 需要 workflow 能力支持以下对象的状态推进：入住、护理计划、探视审批、报警处置、设备验收、物资上架、员工入职。
- 需要审计和回放能力，尤其覆盖 AI 建议、人工确认、规则变更和敏感字段访问。

## Family 输入分析

### 业务特征

- Family 更像“关系绑定后的摘要消费端”，其核心对象不是全量老人档案，而是“家属可见老人视图”。
- 家属侧需要探视、账单、消息、护理记录、健康趋势与 AI 解释，但不应暴露员工内控数据、院内规则或其他住户信息。
- family 工程已经明确后续要从 MockFamilyService 切换到 BFF / API Repository。

### 后端约束

- 需要 Family BFF，将 Elder、Health、Care、Visit、Billing、Notification、AI 等数据裁剪为家属可见模型。
- 需要 relationship scope，确保一个家属只能访问自己绑定住户、授权账单和授权探视记录。
- 需要通知与消息聚合能力，把护理完成、健康异常、探视审批、账单变化收敛为统一家属消息流。
- 需要对 AI 输出进行家属化改写，避免把内部告警、内部评分或非公开风险词直接暴露给家属。

## Nani 输入分析

### 业务特征

- Nani 是移动执行端，核心不在“看板”，而在“任务对象 + 命令动作 + 当前班次上下文”。
- 健康录入、护理执行、报警处理和交接班需要高频写入，且存在弱网络、重复提交、跨班次交接和对象锁定问题。
- AI 在 nani 端只做建议与解释，不应直接改写任务归属或结案结果。

### 后端约束

- 需要 Nani BFF，为移动端提供按班次、按责任人、按优先级聚合的任务和告警入口。
- 需要命令幂等、乐观并发和审计日志，避免重复打卡、重复报警处理和错班次提交。
- 需要 token 刷新、设备绑定、班次上下文、责任人校验等移动执行约束。
- 需要支持“写模型实时入库 + 读模型按班次/对象重组”的 CQRS 风格读写分离。

## 三端共同后端约束

### 统一约束

- 所有端都应通过 gateway 和各自 BFF 访问领域服务，不直接扇出访问微服务。
- 领域服务必须以租户为第一维度建模，tenant context 不能依赖前端页面推断。
- 高风险动作必须保留人工确认，不允许 AI 或规则引擎直接越权改写最终状态。
- 关键状态变化必须事件化，便于消息、AI、报表和审计消费。

### 统一能力清单

- identity and access: 登录、组织、角色、租户、对象级授权。
- tenant management: SaaS 租户、套餐、配置、院区隔离、特性开关。
- command workflow: 入住、探视、报警、护理计划、员工入职、设备验收、物资入库等状态机。
- event backbone: 领域事件、通知分发、报表同步、AI 处理输入。
- observability: trace、audit、tenant metrics、业务 KPI、失败重试。

## 对 backend 工程的直接结论

1. backend 必须采用 BFF + 领域微服务的双层入口，而不是单一 REST 大后端。
2. 后端设计必须优先覆盖 workflow 和状态机，而不是先做平面 CRUD。
3. SaaS 支持必须从第一天纳入：租户解析、数据隔离、套餐开关、租户级配置和租户级审计。
4. AI 相关服务必须定位为 orchestration 和 inference adapter，不能直接成为业务事实源。
5. 后续 API 契约与数据库设计都应从本文提炼的边界继续细化。
