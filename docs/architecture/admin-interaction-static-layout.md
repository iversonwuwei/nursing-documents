# Admin 交互纵向堆叠布局设计

## Scope

- scope: 为 admin 端建立统一的“主工作区在前，补充上下文在后”的纵向页面骨架，落实单列阅读和顺序化决策原则。
- visual standard: 共享视觉层统一向 Microsoft Fluent 2 的企业工作台风格收敛，采用更克制的中性色表面、清晰焦点态与一致的控件层级，但不在本轮引入新的组件库依赖。
- boundaries: 本轮只处理前端页面结构、样式和信息分层，不调整服务契约、接口字段或模块权限模型。
- dependencies: `nursing-admin-v2` 设计系统组件、页面级 `PageHeader` / `DataCard` / `WorkflowOverviewCard`、现有响应式断点。
- rollback: 回退共享布局组件、全局样式和首批接入页面。

## Entry Points

- `/alerts`
- `/financial`
- `/notifications`
- 所有复用 `StandardModulePage` 的标准页路由，例如 `/settings`、`/settings/roles`、`/devices/assets`、`/alerts/history`、`/health/[metric]`、`/nursing/[module]`。
- 所有复用 `dashboard-grid-2` 的自定义工作台页面。
- 第二批高频工作台与经营总览页：`/`、`/organizations`、`/staff`、`/operations/daily`、`/ai-assistant`。
- 第三批自定义详情与协同页：`/organizations/[id]`、`/organizations/partners`、`/supplies/[id]`，统一收口为“对象总览或协同总览在前，状态/帮助/边界在后”。

## Layout Contract

- 页面骨架由两段顺序组成：主工作区先出现，承载当前页主要任务；补充上下文区后出现，承载说明、状态、边界和帮助入口。
- 桌面端与移动端统一采用纵向单列堆叠，不再默认左右分栏，避免同一屏幕内出现两个并行阅读轴。
- 补充上下文区允许放置 API 状态、服务模块说明、workflow 闭环、结构化摘要和回滚说明，但不承担页面唯一关键动作。
- 补充上下文区不再默认展开完整说明文案；说明类内容先经过“是否直接支持当前任务”筛选，只有保留理由明确的内容才留在当前页。
- 单个页面应尽量只承载一个主闭环；如果总览、导航、即时操作或审计复盘属于不同心智任务，应拆成独立页面，而不是在一个页面里强行串联。

## Contextual Help Surface

- 页面级帮助采用“轻量帮助卡 + 独立帮助页”双层结构。
- 轻量帮助卡只保留 2 到 4 条摘要和 1 个入口链接，用来回答“我现在在哪里、下一步先做什么、哪里看完整规则”。
- 独立帮助页承载模块边界、workflow 解释、异常口径、角色责任和培训性说明，避免把工作台本身变成说明书。
- 首批帮助页跟随 `/alerts`、`/financial`、`/notifications` 一起落地，作为 Phase 1 的收口出口。
- 标准页帮助统一通过通用路由 `/help/[...slug]` 生成，避免为每个标准页重复实现一套帮助壳层。
- 自定义高频工作台页面继续使用显式帮助页路由承接长说明，避免把经营摘要、AI 解释和推荐路径重新堆回当前页主工作区。

## Component Strategy

- 共享组件提供统一的纵向容器，避免每个页面自行手写一套堆叠顺序。
- 全局样式负责顺序、间距和响应式节奏，页面只负责把内容归入 `main` 或 `rail`，但两者都按单列顺序展示。
- 视觉令牌、按钮、输入框、导航栏、数据卡和表格统一使用 Fluent 2 风格的轻描边、浅层阴影和可感知焦点反馈，避免继续沿用装饰性过强的渐变卡片语言。
- 页面内部保留原有卡片和业务逻辑，重构目标是信息重排而不是业务抽象重写。
- `StandardModulePage` 现已直接内建主内容区、后置上下文区和帮助入口，标准页不再维持旧的等宽 `dashboard-grid-2` 双栏。
- `dashboard-grid-2` 作为历史上最广泛复用的双栏类，现已统一收敛为纵向堆叠，用于让一批自定义页自动继承同一阅读顺序。
- 高频工作台页若仍需保留多块说明性卡片，优先通过 `InteractionRailLayout` 显式拆成“主区在前 + 上下文区在后”，而不是继续把不同任务混排成并行区域。
- 对象详情页和协同页若仍保留 tab、对象状态、AI 摘要与说明块，应先把对象事实、台账或列表保留在主区，再把 AI 解释、治理边界和帮助入口压到后置上下文区，而不是继续维持主区 + 侧区的双轴竞争。

## Content Placement Rules

- 主工作区: 筛选、搜索、列表、详情、编辑器、备注输入、状态推进按钮、主操作 CTA、与当前任务直接相关的空态和错误态。
- 后置上下文区: API 对接状态、数据源边界、服务模块矩阵、workflow 说明、只读统计、结构占比、回滚路径和健康信号。
- 只读列表若主要承担“解释”和“辅助认知”，优先进入后置上下文区；若承担“下一步决策输入”，保留在主工作区。
- 说明类内容若超过一张卡片或需要用户滚动阅读，优先迁移到帮助页，而不是继续堆叠在当前页面的后置区。
- 后置上下文区保留的数据卡必须满足至少一条：提供实时系统状态、提供决策输入、提供失败边界；否则应移除。
- 交互逻辑若与当前页主任务不一致，应优先拆到独立路由；例如 AI 总览页只保留总览与分流，即时问答拆到 `/ai-assistant/qa`，避免入口页同时承担工具执行。
- 首页这类总览入口页只承载“优先级判断 + 去哪个工作台”的闭环；护理任务表、健康明细、告警明细等执行型或详情型内容应回到各自专页，而不是继续在首页直接处理。
- 详情页的帮助入口优先复用所属模块的帮助页；若现有模块帮助页无法承接当前对象级边界，再补显式帮助路由，而不是把长解释重新塞回详情页首屏。

## Failure Modes

- failure mode: 页面继续使用左右并行布局，导致用户在单屏内来回切换阅读轴，首要任务不清晰。
- failure mode: 后置上下文区放入必须立即点击的主按钮，导致关键动作被推迟到页面下半段。
- failure mode: 操作性错误提示被放到纯说明区，用户无法在主任务附近快速定位失败原因。
- failure mode: 单页仍混入过多并行模块，即使改成单列也无法形成清晰顺序。
- failure mode: 入口页同时承载总览、导航、问答、审计或治理等多种任务，导致用户必须在单页内切换多套心智模型。

## Health Signals

- healthy: 页面从上到下能按“先主任务、后补充上下文”的顺序阅读，不需要在左右区域之间跳转。
- healthy: 后置上下文区能稳定聚合数据源、workflow、说明和只读摘要，不与主任务区争抢首屏优先级。
- healthy: 各尺寸下都保持同一纵向顺序，页面不存在因双栏导致的横向滚动依赖。
- unhealthy: 用户执行主任务仍需在多个等权卡片之间搜索入口，或关键状态散落在不同段落而没有清晰顺序。
- healthy: 完整说明已迁入独立帮助页，当前页后半段只剩必要上下文与帮助入口。
- unhealthy: 页面后半段仍存在多张长说明卡片，需要连续滚动阅读才能找到主要操作。

## Verification

- docs: `npm run docs:build`
- frontend: `npm run lint && npm run build`
- manual:
  1. 用桌面宽度检查服务型页面、标准页和复用 `dashboard-grid-2` 的页面是否稳定按单列顺序呈现主区和后置上下文区。
  2. 检查主 CTA、筛选和列表始终出现在上半段，补充说明和帮助入口后置出现。
  3. 检查 `/help/...` 路由能正确承接标准页说明内容，且当前页不再依赖左右分栏才能理解主次关系。

## Rollback

- 回退共享布局组件和全局样式定义。
- 回退三个页面对主工作区与信息轨的内容分配。
- 保留页面业务逻辑和服务调用，确保回滚只影响 UI 结构。
