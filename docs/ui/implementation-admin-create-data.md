# 实施级文档：管理端新建数据闭环

## 范围

覆盖管理端新建数据的首批实施方案，先以老人创建为第一条可交付闭环，并为机构、房间、活动等后续新建能力提供统一程序设计模板。

## 用户影响

- 前台接待不再把“新增老人”当作孤立档案录入，而是直接进入入住审核链路。
- 护理主管可在同一条记录上完成 AI 建议复核、人工调整和护理计划生成。
- 运营与档案人员可在老人列表和详情页追踪新建对象的当前阶段。

## 页面入口

- 列表入口：`/elderly`
- 新建入口：`/elderly/new`
- 审核入口：`/elderly/checkin`
- 档案入口：`/elderly/[id]`
- 发布阶段：管理端全量开放，当前仍使用 shared mock store，不接真实入院 API

## 程序设计

### 共享状态

- `admission-workflow.ts` 作为创建与入住审核的共享 store。
- `validateAdmissionForm` 统一承接新建页和入住页的校验口径，避免两个表单各自维护规则。
- `addAdmissionApplication`、`confirmAdmissionPlan`、`markAdmissionAsAdmitted` 形成创建状态机。

### 数据分层

| 层级 | 职责 | 当前实现 |
| --- | --- | --- |
| 创建输入层 | 收集首批最小必填字段 | `/elderly/new` 与 `/elderly/checkin` 表单 |
| 审核决策层 | 输出 AI 建议与人工确认结果 | `admission-workflow.ts` |
| 下游同步层 | 派生任务与提醒 | `/staff/tasks`、`/notifications` |
| 台账展示层 | 合并静态老人数据与新建记录 | `elderly-registry.ts`、`/elderly`、`/elderly/[id]` |

### 口径桥接

- 入住闭环使用 `特级/一级/二级/三级护理`。
- 老人台账历史上使用 `特级/全护理/半自理/自理`。
- 当前通过 `elderly-registry.ts` 做映射桥接，保证新建记录进入老人列表时不会破坏现有筛选与标签体系。

### 字段演进策略

- 本次先保证入住评估闭环可执行，保留“最小可执行字段集”。
- 身份证、出生日期、联系人拆分等主数据字段暂未写入 shared mock store。
- 接真实 API 时应把这些字段下沉到主档模型，避免长期停留在“待补录”占位态。

## 状态设计

- 加载态：新建提交按钮展示保存中，入住页按 shared store 即时刷新
- 空态：入住审核页无样本时仍保留新建入口；老人列表无结果时保留搜索空态
- 错误态：统一表单级校验错误；人工改级缺少说明时阻止提交
- 移动端：新建页与入住页采用纵向卡片堆叠，避免双栏依赖

## 扩展规则

- 后续新建机构、房间、活动、事件时，继续复用“录入 -> 审核/确认 -> 下游同步 -> 台账展示”四段式流程。
- 未具备下游同步能力的模块，不应只补一个新增按钮；至少要同步设计其审核与入册出口。

## 发布门禁

- 新建页与入住页必须共享同一套校验规则
- 新建后必须带着对象 ID 跳转到入住审核页
- 标记已入住后必须能在老人列表和详情页看到同一对象
- 当前最小门禁：`npm run lint`
- 当前增强门禁：`npm run lint` 与 `npm run build`

## 回滚方案

1. 回退 `/elderly/new` 对 shared workflow store 的写入。
2. 恢复 `/elderly` 与 `/elderly/[id]` 仅消费静态老人数据。
3. 保留 `/elderly/checkin` 作为独立 demo，不再承接新增老人入口。
